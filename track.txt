================================================================================
  1. PROJECT OVERVIEW
================================================================================

SIF Sentinel AI is an AI-Powered Safety Intelligence Platform designed for
Serious Injury & Fatality (SIF) prevention in industrial environments. It was
built for the Smart India Hackathon 2026 under the problem statement from
Oil India Limited.

The system takes unstructured safety incident narratives (plain text reports)
and transforms them into structured, scored, explainable, and actionable
intelligence. It produces:

  - SIF Probability Score: The likelihood that a given incident narrative
    describes a Serious Injury or Fatality event.
  - Life Saving Rule (LSR) Mapping: Which of the 9 standardised Life Saving
    Rules are relevant to the incident.
  - Hazard / Entity Extraction: Hazards, equipment, activities, and conditions
    automatically extracted from the narrative text.
  - Explainable Risk Scoring: A fused risk band (LOW/MEDIUM/HIGH/CRITICAL) with
    full transparency on how the score was computed.
  - Fatality Twin: An escalation projection chain showing how the incident
    could lead to a fatality, based on matched historical fatal cases.
  - Precedent-Grounded CAPA: Corrective and Preventive Action recommendations
    driven by the specific LSR violations and matched fatal precedents.
  - Safety Memory: An AI system that remembers every incident ever reported and
    automatically compares new reports against the full 16k-record corpus.
  - AI Safety Copilot: A citation-enforced conversational interface that can
    answer complex natural-language queries over the incident corpus.
  - Structured Natural-Language Queries: Multi-constraint filtering through
    natural language (e.g., "Show confined space incidents during monsoon with
    SIF > 90 where gas detector failed").

The system is built end-to-end on two real OSHA (Occupational Safety & Health
Administration) public datasets:
  - osha_incidents.csv: 4,847 mixed-severity incident narratives
  - osha_fatalities.csv: 14,914 confirmed fatality narratives

After cleaning and deduplication, the combined corpus is approximately 16,249
records.

4.1  DATA SOURCES
-----------------

Source 1: osha_incidents.csv
  - Records:          4,847 rows
  - Content:          Mixed-severity incident narratives
  - Key fields:       summary_nr, Abstract Text, Event Description,
                      Degree of Injury, Nature of Injury, Event type,
                      Human Factor, Environmental Factor, Part of Body,
                      End Use, Event Date
  - SIF labelling:    Fatal Degree-of-Injury OR high-severity Nature-of-Injury
                      (Amputation/Crushing, Electrocution, Asphyxiation/Drowning)
  - Post-cleaning:    ~4,700 rows after dedup (exact + near-duplicate removal)
  - SIF positive rate: ~20–25% of cleaned rows

Source 2: osha_fatalities.csv
  - Records:          14,914 rows
  - Content:          Confirmed fatality narratives (outcome is fatal by def.)
  - Key fields:       id, description, incident_date, city, state, plan, citation
  - Used as:          Knowledge base for retrieval / Fatality Twin (not training)
  - Post-cleaning:    ~11,500 rows after dedup

Combined corpus after cleaning: ~16,249 records


4.2  ETL PIPELINE (ml/pipeline/etl.py)
--------------------------------------

File: ml/pipeline/etl.py (298 lines)
Run:  python3 ml/pipeline/etl.py

Stages (following SRS §5.3):
  1. Acquisition:     Reads CSV files from data/raw/
  2. Cleaning:        Removes null bytes, normalises whitespace, expands
                      abbreviations (LOTO → Lock-Out Tag-Out, PTW → Permit-
                      to-Work, PPE → Personal Protective Equipment, TBSA →
                      Total Body Surface Area)
  3. Row consolidation: Detects and merges multi-row narratives from the CSV
                        (some summary_nr values have wrapped text across rows)
  4. Deduplication:   Exact duplicate removal (normalised lowercase text) +
                      near-duplicate removal via cosine similarity on TF-IDF
                      vectors (threshold 0.95). Near-dedup is capped at 6,000
                      rows for memory reasons.
  5. Labelling:       SIF-positive label derived from Degree of Injury == Fatal
                      or Nature of Injury in {Amputation/Crushing, Electrocution,
                      Asphyxiation/Drowning}
  6. Synthetic fields: Site, Area, and Department are deterministically synthesised
                       from a SHA-256 hash of each record's report_id, biased by
                       real keyword signals in the narrative (e.g., "pipeline" →
                       PIPELINE area, "crane" → Drilling Operations dept).
                       All records carry is_synthetic_org_fields=True.
  7. Entity extraction: Hazard, equipment, activity, condition tags + barrier
                        failure flag extracted via ner.py.
  8. Splitting:       70/15/15 stratified split grouped by site to prevent leakage.
                      Fatalities get split="reference" (knowledge base only).

Outputs:
  - data/processed/incidents.parquet
  - data/processed/incidents.jsonl
  - data/processed/fatalities.parquet
  - data/processed/fatalities.jsonl
  - data/processed/etl_summary.json

Site List (9 synthetic sites):

  - Rig-12 Moran (RIG)
  - Rig-03 Kumchai (RIG)
  - Refinery Block A (REFINERY)
  - Refinery Block B (REFINERY)

4.3  NER / ENTITY EXTRACTION (ml/pipeline/ner.py)
-------------------------------------------------

File: ml/pipeline/ner.py (169 lines)

Uses spaCy blank English pipeline + EntityRuler (no downloaded model needed).

Entity types extracted:
  - HAZARD:     27 terms (energized cable, live circuit, confined space
                atmosphere, flammable vapor, toxic gas, arc flash, etc.)
  - EQUIPMENT:  28 terms (crane, forklift, scaffold, junction box,
                circuit breaker, conveyor, pressure vessel, etc.)
  - ACTIVITY:   26 terms (welding, excavation, crane lift, confined space
                entry, electrical maintenance, lockout tagout, etc.)
  - CONDITION:  17 terms (isolation not verified, guard removed, PPE not
                worn, no fall protection, bypassed interlock, etc.)

Token-level patterns (spaCy patterns for multi-word entities):
  - "energized/live + cable/wire/conductor/circuit/line/panel"
  - "guard/guarding + removed/missing/bypassed/inoperable"
  - "fall from + height/elevation/platform/ladder/scaffold/roof"

Barrier-failure detection (16 regex patterns):
  - Energy isolation / LOTO failures
  - Machine guarding / safety device removals
  - Fall protection absence
  - PPE non-compliance
  - Permit-to-work violations
  - Excavation shoring absence
  Calibrated conservatively: fires on ~1% of narratives. Designed to never
  assert a barrier failure that isn't explicitly stated in the text.


4.4  EMBEDDINGS & VECTOR INDEX (ml/pipeline/embeddings.py)
----------------------------------------------------------

File: ml/pipeline/embeddings.py (201 lines)
Run:  python3 ml/pipeline/embeddings.py

SRS specifies Sentence-Transformers (all-MiniLM-L6-v2) for 384-dim embeddings
and MongoDB Atlas Vector Search. Neither is available in this sandbox.

Substitute:
  - Encoder:  TF-IDF (1-2 grams, 60,000 features, sublinear TF) →
              TruncatedSVD(384) = "LSA" embedding. Fit once on the combined
              incidents + fatalities corpus. Pickled as encoder.pkl (~91 MB).
  - Index:    FAISS IndexFlatIP over L2-normalised vectors (cosine similarity).
              Three sub-indices: ALL (all vectors), FATALITY (fatalities only),
              INCIDENT (incidents only). This ensures top-k FATALITY queries
              return genuine nearest fatalities, not an oversample-then-filter
              slice of a mixed index.

Boilerplate stripping: OSHA incident abstracts share a near-fixed preamble
("At 9:00 a.m. on August 10, 2017, an employee was..."). This is stripped
before encoding to prevent template overlap from dominating similarity scores.

Vector count: ~16,249 vectors (4,700 incidents + 11,500 fatalities)
Dimension:    384


4.5  SIF CLASSIFIER (ml/models/train_sif_classifier.py)
-------------------------------------------------------

File: ml/models/train_sif_classifier.py (134 lines)
Run:  python3 ml/models/train_sif_classifier.py

Architecture (preserving SRS §10.1 / SC-1 design):
  1. Text head:       LogisticRegression over TF-IDF (30,000 features, 1-2 grams,
                      balanced class weights, C=2.0, max_iter=2000)
  2. Structured head: XGBoost (300 estimators, depth=4, lr=0.08) over
                      OneHotEncoded area/department/activity + barrier_failure
  3. Blend:           0.65 * P(text) + 0.35 * P(structured)
  4. Calibration:     Isotonic regression fit on validation predictions
  5. Threshold:       Tuned on validation to maximise recall at precision ≥ 0.60

Success criteria targets (SRS §3.3):
  - SC-1 recall target: 0.90
  - SC-1 ROC-AUC target: 0.88

Output: ml/artifacts/sif_classifier.joblib, sif_classifier_metrics.json
Model version: "sif-sentinel-v1.0-tfidf-xgb"

4.7  RISK FUSION (ml/models/risk_fusion.py)
-------------------------------------------

File: ml/models/risk_fusion.py (65 lines)

Formula (SRS §10.2, implemented exactly):
  score = 0.55 * P(SIF)
        + 0.25 * max(LSR_severity_weight * LSR_confidence)
        + 0.10 * barrier_failure_present
        + 0.10 * fatality_similarity_max

Banding:
  - CRITICAL: score >= 0.85  OR  (P(SIF) >= 0.90 AND barrier_failure)
  - HIGH:     score >= 0.65
  - MEDIUM:   score >= 0.40
  - LOW:      otherwise

Escalation override: Any report matching a fatal case at >= 0.90 similarity
is floored at HIGH (cannot be rated lower than HIGH).

LSR Severity Weights:
  - ENERGY_ISOLATION:       1.00
  - CONFINED_SPACE:         1.00
  - WORK_AT_HEIGHT:         0.90
  - LINE_OF_FIRE:           0.90
  - BYPASSING_CONTROLS:     0.85
  - HOT_WORK:               0.80
  - SAFE_MECHANICAL_LIFTING:0.80
  - DRIVING_SAFETY:         0.75
  - WORK_AUTHORISATION:     0.70


4.8  FATALITY TWIN (ml/models/fatality_twin.py)
-----------------------------------------------

File: ml/models/fatality_twin.py (70 lines)

Purpose: Shows the escalation chain from the current incident to a potential
fatality, based on matched historical fatal cases.

Chain construction:
  1. Contact type:  Regex-matched from report text (slip/fall, struck-by,
                    caught-in, electrocution, explosion, asphyxiation,
                    fire/burn, collapse, vehicle contact)
  2. Barrier node:  Only asserted when barrier_failure is actually detected
                    in the report's own text (not assumed)
  3. Outcome:       Counted majority across matched fatality narratives
                    (burns, fracture, head trauma, amputation, asphyxiation,
                    internal injuries)
  4. Terminal:      "Fatality"

Returns: chain array, likelihood (average similarity), matched count,
max similarity, matched_report_ids

4.14  INFERENCE ENGINE (ml/pipeline/inference.py)
-------------------------------------------------

File: ml/pipeline/inference.py (171 lines)

The central InferenceEngine class that ties all AI components together.
Loaded as a singleton in the backend. Used for both:
  - Historical batch scoring (build_analytics_artifacts.py)
  - Live new report scoring (POST /api/v1/incidents)

Steps in InferenceEngine.analyze():
  1. Entity extraction (ner.py)
  2. Synthetic field generation if site/area/department not provided
  3. SIF probability computation (text + structured blend + calibration)
  4. LSR tag mapping (multi-label classification)
  5. Vector encoding of narrative
  6. Similarity search: top-10 fatalities + top-10 incidents
  7. Risk fusion (4-component weighted formula)
  8. Explanation generation (linear-model token attribution — exact, not
     SHAP-approximated, for a logistic regression head)
  9. Root cause classification (PROCEDURE_VIOLATION / EQUIPMENT_FAILURE /
     HUMAN_ERROR)
  10. Fatality Twin construction (from matched fatal cases)
  11. CAPA recommendation generation

Returns a comprehensive analysis dict with 20+ fields.

  8. WHAT IS NOT WORKING / KNOWN LIMITATIONS
================================================================================

  ❌ No real MongoDB — data is in-memory only, lost on restart
     (SRS §6.3/§9 specifies MongoDB)

  ❌ No real Sentence-Transformer embeddings — using TF-IDF/SVD instead
     (SRS §7.2 specifies all-MiniLM-L6-v2)

  ❌ No real LLM for Copilot — using intent-routed extractive/template
     answering instead of LangChain RAG (SRS §10.3/§12.2)

  ❌ No LLM-backed NER fallback — using gazetteer + regex only
     (SRS §10.1 specifies LLM back-fill for unseen phrasing)

  ❌ No real user authentication — no login/signup system
     (SRS mentions role-based access control)

  ❌ No real-time notification system — no WebSocket push
     (SRS mentions real-time alerts)

  ❌ No email/SMS alert integration
     (SRS mentions notification channels)

  ❌ No audit trail / change history logging
     (SRS mentions audit capabilities)

  ❌ Map heatmap uses synthetic coordinates
     (Real site coordinates would come from OIL's internal data)

  ❌ Site/Area/Department fields are all synthetic
     (OSHA data doesn't carry these fields)

  ❌ Forecast timeline is synthetic
     (OSHA data dates don't represent a continuous recent timeline)

  ⚠️  Near-duplicate removal capped at 6,000 rows
     (Memory constraint for dense pairwise cosine similarity)

  ⚠️  Barrier failure detection fires on only ~1% of narratives
     (Conservative by design — OSHA abstracts rarely state which control failed)

  ⚠️  Live submissions are in-memory only (lost on server restart)

  ⚠️  No production HTTPS — runs on HTTP locally

  ⚠️  No rate limiting on API endpoints

  ⚠️  Frontend does not have a mobile-optimised responsive layout for phones
     (Sidebar-based layout optimised for desktop/tablet)


================================================================================
  9. KNOWN DEVIATIONS FROM SRS
================================================================================

Full documentation: docs/DEVIATIONS.md (9,887 bytes)

Key deviations:
  1. MongoDB → In-memory store (no outbound access to MongoDB Atlas)
  2. Sentence-Transformers → TF-IDF/SVD (no access to huggingface.co)
  3. DistilBERT → LogisticRegression text head (same architecture, swap only)
  4. LLM Copilot → Intent-routed extractive answering (no LLM endpoint)
  5. LLM NER back-fill → Omitted (gazetteer + regex only)
  6. MinHash near-dedup → Dense cosine (capped at 6,000 rows)
  7. Atlas Vector Search → FAISS IndexFlatIP (offline equivalent)
  8. Real site/area/department → Synthetic (OSHA data lacks these fields)
  9. Real forecast timeline → Synthetic (dates don't represent recent periods)

All deviations are:
  - Documented in docs/DEVIATIONS.md
  - Disclosed through is_synthetic_org_fields / is_synthetic_timeline flags
  - Designed to preserve the same architecture and API contracts
  - Swappable for real implementations without changing any caller
