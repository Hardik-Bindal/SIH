1. PROJECT OVERVIEW & VISION
================================================================================

KAVACH AI (Knowledge-driven AI for Vigilance and Critical Hazard Prevention) is
an end-to-end AI-powered industrial safety intelligence platform built for the
Smart India Hackathon 2026. It was developed by Team "The Last Commit" for the
Oil India Limited problem domain.

THE CORE IDEA:
Every day, safety incidents are reported as free-text narratives in industrial
organisations. These narratives are reviewed in isolation — the fourth
occurrence of the same hazard pattern is investigated as if it were the first.
Nobody connects the dots across thousands of past reports. KAVACH AI solves
this by:

1. Taking unstructured safety narratives (plain English text describing what
   happened) and automatically turning them into STRUCTURED, SCORED,
   EXPLAINABLE, and ACTIONABLE intelligence.

2. Every single report is automatically:
   - Scored for SIF (Serious Injury or Fatality) probability
   - Mapped to Life Saving Rules (IOGP Report 459)
   - Enriched with extracted hazards, equipment, activities, conditions
   - Risk-banded (LOW / MEDIUM / HIGH / CRITICAL)
   - Compared against 16,249 historical records for precedent
   - Checked for barrier failures (safety controls that failed)
   - Given a "Fatality Twin" escalation projection
   - Given precedent-grounded CAPA (Corrective and Preventive Actions)
   - Presented with explainability (why the AI scored it this way)

3. The system provides a Safety Copilot that answers natural-language
   questions with citations to real reports — never fabricates answers.

THE TWO REAL DATASETS:
- osha_incidents.csv: 4,847 mixed-severity incident narratives from OSHA
- osha_fatalities.csv: 14,914 confirmed fatality narratives from OSHA
Combined: 16,249+ real records (after deduplication)

FULL SRS REFERENCE: docs/SIF_Sentinel_AI_SRS_v2.docx


================================================================================
2. PROBLEM STATEMENT & WHY THIS MATTERS
================================================================================

IN INDUSTRIAL SAFETY TODAY:
- Incident reports are written as free text, reviewed manually, one at a time
- The 4th occurrence of the same hazard is investigated as if it were the 1st
- Nobody asks "has this happened before?" automatically
- Nobody asks "what keeps happening across our entire operation?"
- Filter-based dashboards cannot answer compound questions like:
  "Show all confined space incidents during monsoon with SIF > 90 where gas
   detector failed"
- Safety bulletins are manually authored
- No system connects a current near-miss to historical fatalities to show
  "this exact scenario has killed someone before"

WHAT KAVACH AI DOES DIFFERENTLY:
1. SAFETY MEMORY: Every new report is AUTOMATICALLY compared against ALL
   16,249 records the moment it is filed. Nobody has to think to ask "has
   this happened before?" — it is answered proactively.

2. STRUCTURED NATURAL-LANGUAGE QUERY: Instead of clicking through filter
   dropdowns, an officer can type a complex question in plain English and
   get an aggregate answer with citations.

3. FATALITY TWIN: Shows that the current near-miss is on the same escalation
   chain as a confirmed historical fatality.

4. CITATION GUARDRAIL: The Copilot NEVER fabricates. If it cannot back its
   answer with a real report_id from the corpus, it explicitly says so
   (grounded: false).

4. DATA LAYER — RAW DATASETS
================================================================================

LOCATION: data/raw/

FILE 1: osha_incidents.csv (4,847 rows, ~3.4 MB)
-------------------------------------------------
This is a real OSHA (Occupational Safety and Health Administration) public
dataset of mixed-severity workplace incidents. Key columns:

- summary_nr: Unique identifier for each incident
- Abstract Text: Free-text narrative describing what happened
- Event Description: Additional event details
- Degree of Injury: Severity classification (e.g., "Fatal", "Hospitalized")
- Nature of Injury: Type of injury (e.g., "Amputation, Crushing", "Fractures")
- Event type: Classification (e.g., "Struck-by", "Fall (from elevation)")
- Human Factor: Contributing human factor
- Environmental Factor: Environmental conditions
- Part of Body: Body part affected
- Event Date: When the incident occurred
- End Use: Industry context (e.g., "Construction")

This corpus is used for:
- Training the SIF (Serious Injury or Fatality) classifier
- Training the LSR (Life Saving Rule) mapper
- As the operational corpus for the dashboard
- As part of the vector index for similarity search

FILE 2: osha_fatalities.csv (14,914 rows, ~1.8 MB)
----------------------------------------------------
This is a real OSHA public dataset of confirmed workplace fatalities. Key columns:

- id: Unique identifier
- description: Free-text narrative of the fatal incident
- incident_date: When it happened
- city, state: Location
- plan, citation: Jurisdiction/citation flags

This corpus is used as:
- The KNOWLEDGE BASE for similarity retrieval
- The reference for the "Fatality Twin" escalation projection
- Part of the Safety Memory corpus for precedent matching
- Evidence base for CAPA (Corrective/Preventive Actions)

IMPORTANT: Neither dataset carries site/area/department metadata (they are
public OSHA datasets, not Oil India's internal system). These fields are
DETERMINISTICALLY SYNTHESISED and DISCLOSED as synthetic via the
is_synthetic_org_fields flag on every record.

PROCESSED DATA: data/processed/
After ETL, the cleaned and enriched data is saved as both .parquet (binary,
fast for pandas) and .jsonl (JSON lines, human-readable) formats.
- incidents.parquet / incidents.jsonl: Cleaned incidents with NER enrichment
- fatalities.parquet / fatalities.jsonl: Cleaned fatalities with NER enrichment
- etl_summary.json: Summary statistics of the ETL run

5. ML PIPELINE — FULL EXPLANATION OF EVERY FILE
================================================================================

The ML pipeline is in ml/pipeline/ and contains four core modules that are
shared between the batch-processing path (training/scoring the historical
corpus) and the live inference path (scoring a brand-new report submitted
through the API).


--------------------------------------------------------------------------------
5.1 ETL Pipeline — ml/pipeline/etl.py (298 lines, 13 KB)
--------------------------------------------------------------------------------

PURPOSE: Implements SRS section 5.3 — the data pipeline that transforms raw
CSV data into clean, enriched, labelled, and split datasets ready for ML.

STAGES:
1. ACQUISITION: Reads osha_incidents.csv and osha_fatalities.csv from data/raw/
2. CLEANING: The _clean_text() function:
   - Removes null bytes, normalises whitespace
   - Expands safety abbreviations (LOTO → Lock-Out Tag-Out, PTW → Permit-to-Work,
     PPE → Personal Protective Equipment, TBSA → Total Body Surface Area)
   - Filters out narratives shorter than 15 characters
3. DE-DUPLICATION:
   - _dedupe_exact(): Removes exact duplicate narratives (case-insensitive)
   - _dedupe_near(): Uses TF-IDF cosine similarity to find near-duplicates
     (threshold=0.95). Only runs on corpora small enough for dense pairwise
     comparison (capped at 6,000 rows).
   - _consolidate_wrapped_rows(): Fixes CSV parsing issues where long narratives
     were split across multiple rows sharing the same summary_nr
4. ENRICHMENT:
   - Applies Named Entity Recognition (extract_entities from ner.py) to
     extract hazard tags, equipment tags, activity, conditions, barrier failures
   - Synthesises site/area/department from a hash of the report_id, biased by
     content keywords where they carry signal
5. LABELLING:
   - sif_positive: Binary label. 1 if Degree of Injury == "Fatal" OR
     Nature of Injury is in {Amputation/Crushing, Electrocution, Asphyxiation/Drowning}
   - report_type: INCIDENT (if sif_positive=1) or NEAR_MISS
6. SPLITTING:
   - stratified_split(): 70/15/15 train/val/test split, GROUPED BY SITE to
     prevent data leakage (SRS 5.3 stage 6). This means all reports from a
     given site are in the same split — no site appears in both train and test.

KEY FUNCTIONS:
- synth_site_area(report_id, text_hint): Deterministic site/area synthesis
  using SHA-256 hash. If the narrative mentions keywords like "pipeline" or
  "refinery", the site selection is biased toward matching sites.
- synth_department(report_id, text_hint): Similar, using keyword patterns
  (e.g., "electric|cable|wire" → Electrical Maintenance)
- process_incidents(): Full pipeline for the incidents corpus
- process_fatalities(): Full pipeline for the fatalities corpus

OUTPUT:
- data/processed/incidents.parquet and .jsonl
- data/processed/fatalities.parquet and .jsonl
- data/processed/etl_summary.json

RUN: python3 ml/pipeline/etl.py


--------------------------------------------------------------------------------
5.2 Named Entity Recognition — ml/pipeline/ner.py (268 lines, 16 KB)
--------------------------------------------------------------------------------

PURPOSE: Gazetteer-driven entity extraction for safety narratives. Implements
SRS 10.1 ("spaCy pipeline augmented with a curated safety gazetteer").

ARCHITECTURE:
- Uses a BLANK spaCy English pipeline (no downloaded model weights needed)
- Adds an EntityRuler with curated pattern lists
- Also uses regex-based barrier failure detection

ENTITY TYPES EXTRACTED:
1. HAZARD (27 terms): energized cable, live circuit, confined space atmosphere,
   flammable vapor, toxic gas, falling object, etc.
2. EQUIPMENT (28 terms): crane, forklift, scaffold, junction box, pressure
   vessel, chainsaw, nail gun, etc.
3. ACTIVITY (26 terms): welding, excavation, crane lift, confined space entry,
   lockout tagout, etc.
4. CONDITION (17 terms): isolation not verified, guard removed, ppe not worn,
   no fall protection, etc.
5. CONTROL (36 terms): atmospheric testing, gas detector, standby attendant,
   fall harness, lockout tagout, fire watch, etc.

BARRIER FAILURE DETECTION:
Uses 20+ regex patterns to detect when a safety control was absent or failed.
Examples:
- "not locked out" → Energy isolation failure
- "guard removed" or "guard missing" → Machine guarding failure
- "not wearing a harness" → Fall protection failure
- "no permit" → Permit to work failure
- "atmospheric testing not completed" → Confined space control failure

The patterns are conservative and precise: a missing barrier flag means "this
narrative does not STATE a failed control", not "no barrier failed".

FAILED CONTROL DETECTION:
An additional layer of 40+ regex patterns detects SPECIFIC failed controls
with human-readable labels:
- "Gas monitoring" — gas detector not available/used
- "Standby attendant" — attendant absent
- "Entry permit" — no entry/confined space permit
- "Fall arrest harness" — not wearing/using fall protection
- "Energy isolation / LOTO" — lockout not performed
- "Machine guarding" — guard removed/missing
- "Ventilation" — ventilation not provided
- etc.

KEY FUNCTION:
extract_entities(text) → Returns dict with keys:
  hazard, equipment, activity, condition, control, barrier_failure, failed_controls

This function is called BOTH during batch ETL AND during live inference,
ensuring every report goes through identical extraction logic.


--------------------------------------------------------------------------------
5.3 Embeddings & Vector Index — ml/pipeline/embeddings.py (201 lines, 8 KB)
--------------------------------------------------------------------------------

PURPOSE: Creates 384-dimensional narrative embeddings and a FAISS vector index
for semantic similarity search across the entire corpus.

SRS SPECIFICATION vs IMPLEMENTATION:
- SRS specifies: Sentence-Transformers all-MiniLM-L6-v2 (384-dim) served
  through MongoDB Atlas Vector Search
- Actual: TF-IDF (1-2 grams, 60K features) → TruncatedSVD(384) ("LSA
  embedding") + FAISS IndexFlatIP. Reason: No outbound access to
  huggingface.co to download transformer weights. See docs/DEVIATIONS.md.
- The interface is IDENTICAL: encode_one(), encode_many(), search() work the
  same way, so a real sentence-transformer could be dropped in later.

CLASS: NarrativeEncoder
- fit(texts): Fits TF-IDF vectorizer + TruncatedSVD on the combined corpus
- encode(texts) → np.ndarray: Transforms texts to 384-dim L2-normalised vectors
- encode_one(text) → np.ndarray: Single text encoding
- save(path) / load(path): Pickle serialisation

BOILERPLATE STRIPPING:
OSHA incident abstracts share a near-fixed template preamble ("At 9:00 a.m.
on August 10, 2017, an employee was..."). This is stripped BEFORE encoding
because it dominates cosine similarity purely on template overlap, drowning
out actual content similarity. The stored/displayed narrative is untouched.

CLASS: VectorIndex
- Uses FAISS IndexFlatIP (inner product on L2-normalised vectors = cosine sim)
- Maintains SEPARATE sub-indices per source type:
  - "ALL": Every vector (for unfiltered queries)
  - "INCIDENT": Only incident vectors
  - "FATALITY": Only fatality vectors
  This ensures a "FATALITY-filtered" query returns the genuine top-k nearest
  fatalities, not an oversample-then-filter slice that starves the minority.
- search(query_vec, top_k, source_type, site, area): Returns sorted matches
  with similarity scores
- Supports site/area filtering by oversampling then post-filtering

BUILD PROCESS:
1. Read processed incidents.parquet and fatalities.parquet
2. Fit encoder on combined narratives (both corpora together)
3. Encode all narratives to 384-dim vectors
4. Build FAISS indices (ALL, INCIDENT, FATALITY)
5. Save everything to ml/artifacts/

OUTPUT:
- ml/artifacts/encoder.pkl (~91 MB)
- ml/artifacts/incident_vectors.npy
- ml/artifacts/fatality_vectors.npy
- ml/artifacts/vector_index.faiss.ALL
- ml/artifacts/vector_index.faiss.INCIDENT
- ml/artifacts/vector_index.faiss.FATALITY
- ml/artifacts/vector_meta.json

RUN: python3 ml/pipeline/embeddings.py

5.4 Inference Engine — ml/pipeline/inference.py (316 lines, 15 KB)
--------------------------------------------------------------------------------

PURPOSE: The single-report live analysis function. This is THE one function
the backend calls for BOTH new reports submitted via the API AND for batch-
scoring the historical corpus. It ties together EVERY AI component.

CLASS: InferenceEngine (singleton, loaded once at startup)

LOADED ARTIFACTS:
- encoder.pkl (NarrativeEncoder)
- vector_index.faiss + vector_meta.json (VectorIndex)
- sif_classifier.joblib (text pipeline + column transformer + XGBoost + isotonic)
- lsr_mapper.joblib (vectorizer + multi-label classifier + labels)

METHOD: analyze(narrative, site, area, department, activity, report_id)

PROCESSING STEPS (in order):

STEP 1 — Entity Extraction:
  Calls extract_entities(narrative) from ner.py to get hazards, equipment,
  activities, conditions, controls, barrier_failure, failed_controls.

STEP 2 — Organisational Metadata:
  If site/area/department not provided, synthesises them deterministically
  using synth_site_area() and synth_department() from etl.py.

STEP 3 — SIF Probability:
  a) Text pipeline: TF-IDF → LogisticRegression predicts P(SIF) from text
  b) Structural pipeline: OneHotEncoder(area, department, activity) +
     barrier_failure → XGBoost predicts P(SIF) from structured features
  c) Blended: 0.65 * P_text + 0.35 * P_struct
  d) Calibrated: Isotonic regression on the blended score (fitted on
     validation set) produces a calibrated probability

STEP 4 — Contextual Risk Adjustment:
  A post-classifier layer that checks whether the narrative contains concrete
  evidence of an active SIF precursor before accepting a high model score.
  - If ANY SIF-positive signal is present (fatal, electrocution, fall from
    height, confined space entry, etc.) → keep model probability
  - If ZERO SIF signals AND ≥2 routine-observation signals (overdue tag,
    routine inspection, good condition) → cap probability at 0.25
  - Both the original and adjusted probability are returned transparently

STEP 5 — LSR Tags:
  TF-IDF → OneVsRest LogisticRegression gives per-rule probabilities.
  Candidates above 0.20 floor are kept, sorted best-first.
  Returns at most 1 primary + 2 related rules (with secondary 0.30 threshold).

STEP 6 — Vector Embedding + Similarity Search:
  Encodes the narrative, then queries the FAISS index for:
  - Top 10 similar fatalities
  - Top 10 similar incidents

STEP 7 — Risk Fusion:
  Calls fuse() from risk_fusion.py with P(SIF), LSR tags, barrier_failure,
  and max fatality similarity. Produces risk_band and risk_score.

STEP 8 — Explanation:
  Linear-model token attribution. For a logistic regression head over TF-IDF,
  contribution_j = coefficient_j × tfidf_value_j is the EXACT per-feature
  attribution. Returns top 6 contributing terms with weights.

STEP 9 — Root Cause Detection:
  Determines primary contributing factor category:
  - CONTROL_FAILURE: if failed controls detected
  - PROCEDURE_VIOLATION: if barrier failure detected
  - EQUIPMENT_RELATED: if LSR is mechanical lifting or hot work
  - HAZARDOUS_CONDITION: if conditions detected
  - CONTRIBUTING_FACTORS_DETECTED: fallback

STEP 10 — Fatality Twin:
  Calls build_twin() from fatality_twin.py with the matched fatalities to
  build an escalation chain projection.

STEP 11 — Recommendations:
  Calls generate() from recommendations.py to produce corrective actions,
  preventive actions, training needs, and toolbox talk.

STEP 12 — Hash + Version:
  Computes SHA-256 hash of narrative for audit trail, attaches model version.

FULL OUTPUT: A dict with 30+ fields including all of the above.

6.1 SIF Classifier Training — ml/models/train_sif_classifier.py (134 lines)
--------------------------------------------------------------------------------

PURPOSE: Trains the SIF (Serious Injury or Fatality) probability classifier.
This is SRS 10.1 / Success Criterion SC-1.

SUCCESS CRITERIA:
- SC-1 recall target: 0.90
- SC-1 ROC-AUC target: 0.88

6.3 LSR Rules — ml/models/lsr_rules.py (94 lines)
--------------------------------------------------------------------------------

PURPOSE: Keyword heuristics for weak-labelling incidents with Life Saving Rules
from the IOGP Report 459 taxonomy.

THE 9 LIFE SAVING RULES:
1. ENERGY_ISOLATION: lockout, tagout, energized, live circuit, stored energy
2. WORK_AT_HEIGHT: fall from, scaffold, ladder, harness, guardrail, roof
3. CONFINED_SPACE: confined space, atmospheric test, toxic gas, oxygen deficient
4. LINE_OF_FIRE: struck by, caught in, caught between, falling object, crush
5. SAFE_MECHANICAL_LIFTING: crane, hoist, suspended load, rigging, forklift
6. HOT_WORK: welding, cutting torch, hot work, open flame, flammable vapor
7. WORK_AUTHORISATION: permit to work, PTW, unauthorized work, no permit
8. BYPASSING_CONTROLS: guard removed/missing/bypassed, safety device bypassed
9. DRIVING_SAFETY: vehicle accident/collision, driving, seatbelt, speeding

Also uses real structured fields from the OSHA data:
- Human Factor → Rule mapping (e.g., "Safety Devices Removed/Inoperable" →
  BYPASSING_CONTROLS, "Lockout/Tagout Procedure Malfunction" → ENERGY_ISOLATION)
- Event type → Rule mapping (e.g., "Struck-by" → LINE_OF_FIRE,
  "Fall (from elevation)" → WORK_AT_HEIGHT)

6.4 Risk Fusion — ml/models/risk_fusion.py (65 lines)
--------------------------------------------------------------------------------

PURPOSE: Multi-signal risk band computation, exactly as SRS 10.2 specifies.

FORMULA:
  score = 0.55 × P(SIF)
        + 0.25 × max(LSR_severity_weight)
        + 0.10 × barrier_failure_present
        + 0.10 × fatality_similarity_max

RISK BANDS:
  CRITICAL: score ≥ 0.85 OR (P(SIF) ≥ 0.90 AND barrier_failure)
  HIGH:     score ≥ 0.65
  MEDIUM:   score ≥ 0.40
  LOW:      otherwise

ESCALATION OVERRIDE: Any report matching a fatal case at ≥ 0.90 similarity
is floored at HIGH (never below), regardless of the score formula.

LSR SEVERITY WEIGHTS (historically most associated with fatal outcomes):
  ENERGY_ISOLATION: 1.00    CONFINED_SPACE: 1.00    WORK_AT_HEIGHT: 0.90
  LINE_OF_FIRE: 0.90       BYPASSING_CONTROLS: 0.85  HOT_WORK: 0.80
  SAFE_MECHANICAL_LIFTING: 0.80  DRIVING_SAFETY: 0.75  WORK_AUTHORISATION: 0.70

6.5 Fatality Twin — ml/models/fatality_twin.py (70 lines)
--------------------------------------------------------------------------------

PURPOSE: Builds the "Fatality Twin" — an escalation chain showing how a
current near-miss could progress to a fatality, grounded in matched fatal cases.

HOW IT WORKS:
1. Takes the report's narrative and its matched fatalities from similarity search
2. Detects the CONTACT TYPE from the report (9 patterns):
   - Fall, Struck by object, Caught in/crushed, Electrical contact, Explosion,
     Asphyxiation, Fire/burn, Structural collapse, Vehicle contact
3. Counts the most common OUTCOME across matched fatalities (8 patterns):
   - Severe burns, Fracture, Head trauma, Amputation, Asphyxiation,
     Internal injuries, Fatal injury
4. Builds a 4-node escalation CHAIN:
   [Contact Type] → [Barrier Status] → [Common Outcome] → [Fatality]

HONESTY PRINCIPLE: The barrier node only asserts a failure if one was actually
detected in the report. If barrier_failure is False, the chain says "No
confirmed barrier failure in this report's narrative" instead of manufacturing
one.

6.6 Recommendations / CAPA — ml/models/recommendations.py (113 lines)
--------------------------------------------------------------------------------

PURPOSE: Generates Corrective and Preventive Actions (CAPA) and Toolbox Talks,
grounded in the LSR rules violated and the matched fatal precedents.

FOR EACH OF THE 9 LSR RULES, there is a complete action template:
- corrective: Immediate action to stop the hazard
- preventive: Systemic action to prevent recurrence
- training: Awareness/refresher session topic

Example for ENERGY_ISOLATION:
  corrective: "Verify and physically test isolation (lock-out/tag-out) before
               any work resumes on this equipment."
  preventive: "Audit lock-out/tag-out compliance across the department; refresh
               isolation-verification training."
  training:   "Energy Isolation (LOTO) refresher for all crew members."

TOOLBOX TALK: Auto-generated 5-minute toolbox talk with:
- Title based on the primary violated rule
- 4 talking points referencing the specific hazard, equipment, barrier, and
  matched fatal precedent

PRECEDENT NOTE: Always states whether the actions are "grounded in N matched
fatal case(s)" or "rule-based only (no matching fatal precedent)".

6.9 Pattern Clusters — ml/models/pattern_clusters.py (203 lines)
--------------------------------------------------------------------------------

PURPOSE: Discovers recurring patterns across the ENTIRE corpus — "the
incidents nobody realised were the same event."

METHOD:
1. KMeans clustering (N=28) over 384-dim narrative embeddings of the FULL
   corpus (incidents + fatalities together)
2. For each cluster, derives:
   - Dominant Life Saving Rule
   - Barrier failure rate
   - Fatal vs incident mix
   - Sites affected and date range
   - Human-readable label from top TF-IDF terms

RANKING: Patterns are ranked by a composite severity score:
  0.35 × mix_ratio (incident-to-fatality balance)
  + 0.25 × fatal_rate
  + 0.25 × relative_size
  + 0.15 × site_spread
A pattern is "actionable" when: ≥10 incidents AND ≥10 fatalities AND
mix_ratio ≥ 0.15 (real mix, not rounding error).

  INTENT ROUTING (checked in order):

  2. Structured Query: Multi-constraint questions (≥2 constraints)

MEMORY SERVICE (memory.py — 268 lines):
  Safety Memory — "an AI that remembers every safety incident ever reported."

  recall(narrative, exclude_id, top_k) → dict:
  1. Encodes narrative, searches FAISS index for similar records
  2. Applies match floor (0.30) — below this, the match is noise

10. COMPLETE DATA FLOW & WORKFLOW
================================================================================

=== FLOW 1: ML PIPELINE BUILD (one-time) ===

  Raw CSVs ──→ ETL (etl.py) ──→ Cleaned Parquet/JSONL
       │
       ├── Entity Extraction (ner.py) applied per narrative
       ├── Weak labelling (lsr_rules.py) for LSR rules
       ├── Site/area/department synthesis
       └── Stratified train/val/test split

  Cleaned Data ──→ Embeddings (embeddings.py) ──→ Encoder + Vector Index
       │
       ├── TF-IDF fit on combined corpus
       ├── SVD(384) dimensionality reduction
       └── FAISS index built (ALL + per source type)

  Cleaned Data ──→ SIF Classifier (train_sif_classifier.py) ──→ sif_classifier.joblib
       │
       ├── Text pipeline (TF-IDF → LogReg)
       ├── Structured pipeline (OneHot → XGBoost)
       ├── Blended 65/35, isotonic calibrated
       └── Threshold tuned on validation

  Cleaned Data ──→ LSR Mapper (train_lsr_mapper.py) ──→ lsr_mapper.joblib
       │
       └── TF-IDF → OneVsRest LogReg on weak labels

  Cleaned Data + All Artifacts ──→ Batch Scoring (build_analytics_artifacts.py)
       │
       ├── Score every incident through InferenceEngine
       ├── Precompute dashboard aggregates
       ├── Build 7-day forecasts
       ├── Build knowledge graph
       └── Build recurring pattern clusters

=== FLOW 2: BACKEND STARTUP ===

  FastAPI app starts
       │
       ├── database.py: Connect to MongoDB Atlas (or fallback to memory-only)
       ├── store.py: Load incidents_scored.jsonl (16K+ scored incidents)
       │             Load fatalities.parquet (14K+ fatality records)
       │             Load forecast.json, graph.json
       │             Merge any persisted LIVE_SUBMISSION from MongoDB
       └── inference.py: Load encoder, vector index, SIF classifier, LSR mapper

=== FLOW 3: LIVE INCIDENT SUBMISSION ===

  User types narrative in frontend
       │
       ↓
  POST /api/v1/incidents { narrative, site?, area?, department? }
       │
       ↓
  InferenceEngine.analyze()
       │
       ├── 1. extract_entities(narrative) → hazards, equipment, barriers
       ├── 2. Synthesise site/area/department if not provided
       ├── 3. SIF probability (text + structured blend → calibrated)
       ├── 4. Contextual risk adjustment
       ├── 5. LSR tags (multi-label classification)
       ├── 6. Vector similarity search (FAISS → top 10 fatalities + incidents)
       ├── 7. Risk fusion (4-signal weighted formula → band)
       ├── 8. Explanation (token attribution)
       ├── 9. Root cause detection
       ├── 10. Fatality Twin (escalation chain)
       └── 11. Recommendations (CAPA + toolbox talk)
       │
       ↓
  Safety Memory recall (AUTOMATIC — every new report)
       │
       ├── Encode narrative, search FAISS
       ├── Find matches above floor
       ├── Compute common cause
       ├── Determine verdict
       └── Assign to pattern cluster
       │
       ↓
  Response returned to frontend (full AIAnalysis + safety_memory)
       │
  Simultaneously:
       ├── Appended to in-memory store (immediate analytics update)
       └── Upserted to MongoDB (persistence across restarts)

=== FLOW 4: COPILOT QUERY ===

  User types question
       │
       ↓
  POST /api/v1/copilot/query
       │
       ↓
  Intent routing:
       │
       ├── Memory recall? → Safety Memory service
       ├── Multi-constraint? → Structured query engine
       ├── Contains report ID? → Report lookup
       ├── "Riskiest site?" → Site ranking from aggregates
       ├── "CAPA?" → Generate recommendations
       ├── "Summary?" → KPI summary
       ├── "Barrier?" → Barrier centrality analysis
       ├── "Compare X vs Y?" → Side-by-side comparison
       └── None of the above → Semantic vector search fallback
       │
       ↓
  Answer with citations (or explicit refusal if ungrounded)

=== FLOW 5: STRUCTURED QUERY ===

  "Show all confined space incidents during monsoon with SIF > 90 where gas
   detector failed"
       │
       ↓
  Parse:
       ├── topic: CONFINED_SPACE
       ├── season: monsoon (June-September)
       ├── sif: > 0.90
       └── condition: "gas detector" (failed)
       │
       ↓
  Build predicates (one per constraint)
       │
       ↓
  Filter corpus with AND of all predicates
       │
       ↓
  If results: aggregate + report list
  If 0 results: relax each filter → find binding constraint

14. TWO FLAGSHIP DIFFERENTIATORS
================================================================================

DIFFERENTIATOR 1: SAFETY MEMORY
"An AI that remembers every safety incident ever reported."

TODAY'S PROBLEM: Every report is reviewed in isolation. The 4th occurrence of
a pattern is investigated as if it were the 1st. Nobody connects the dots.

HOW IT WORKS:
- Every new report is AUTOMATICALLY compared against ALL 16,249 records
- Nobody has to think to ask "has this happened before?" — it comes back
  automatically as part of the submission response
- Three questions answered:
  1. Has this happened before? → Ranked matches with similarity scores
  2. What was the common cause? → Counted majority across matches (always
     shown as "3 of 8" so a plurality never reads as a law)
  3. What should be done? → Precedent-driven action for the violated rule
- Also clusters the entire corpus into 28 recurring patterns
- Each pattern shows incident/fatality mix, sites affected, date range
- New reports are assigned to their pattern via centroid dot product

DIFFERENTIATOR 2: STRUCTURED NATURAL-LANGUAGE QUERY
"Ask instead of building a dashboard."

TODAY'S PROBLEM: A question like "Show all confined space incidents during
monsoon having SIF > 90 where gas detector failed" carries FOUR independent
constraints that NO filter bar composes.

HOW IT WORKS:
- The Copilot parses the question into an explicit filter object
- Each constraint becomes a named predicate
- All predicates are ANDed to filter the corpus
- Returns: count, most common site, which control keeps failing
- TWO HONESTY PROPERTIES:
  1. The parsed filter is shown back to the user
  2. Anything it couldn't interpret is reported, not silently dropped
- ZERO-RESULT HANDLING: Instead of "no results", relaxes each constraint in
  turn to name the binding one ("0 match all four — dropping 'gas detector'
  alone returns 4")

15. HOW TO RUN THE PROJECT (STEP BY STEP)
================================================================================

PREREQUISITES:
- Python 3.11+
- Node.js 18+
- pip, npm
- (Optional) MongoDB Atlas account for persistence

STEP 1: Build the ML pipeline (one-time, produces everything under ml/artifacts/)

  pip install -r backend/requirements.txt

  python3 ml/pipeline/etl.py                       # Clean, label, split corpora
  python3 ml/pipeline/embeddings.py                # Fit encoder + build vector index
  python3 ml/models/train_sif_classifier.py        # SIF classifier (SC-1)
  python3 ml/models/train_lsr_mapper.py            # LSR mapper (SC-2)
  export OMP_NUM_THREADS=1                         # macOS ARM only
  python3 ml/models/build_analytics_artifacts.py   # Batch score + dashboard artifacts
  python3 ml/models/pattern_clusters.py            # Safety Memory patterns

  NOTE: The artifacts are already committed to git, so this step is only
  needed if you want to regenerate them from scratch.

STEP 2: Run the backend

  cd backend
  uvicorn app.main:app --reload --port 8000
  # → http://localhost:8000/api/v1/health
  # → http://localhost:8000/docs (OpenAPI interactive documentation)

STEP 3: Run the frontend

  cd frontend
  npm install
  npm run dev
  # → http://localhost:5173

STEP 4 (Alternative): Run both with Docker

  docker compose up --build
  # Backend at http://localhost:8000
  # Frontend at http://localhost:5173

STEP 5 (Optional): Configure MongoDB persistence

  cp backend/.env.example backend/.env
  # Edit backend/.env with your MongoDB Atlas credentials
  # Restart the backend

ONE-COMMAND DEMO START:
  bash scripts/demo_start.sh
